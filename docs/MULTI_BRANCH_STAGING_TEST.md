# Multi-Branch — Staging Activation Test Runbook
# سيناريو تفعيل تعدّد الفروع على staging (خطوة بخطوة)

الهدف: تفعيل `BRANCHES_ENABLED=true` على **staging فقط**، والتحقّق end-to-end قبل
الإنتاج. كل خطوة لها **النتيجة المتوقّعة** — أوقف التنفيذ وأبلغ عند أي انحراف.

> القاعدة الذهبية: لا تُفعّل على الإنتاج إلا بعد اجتياز كل بنود هذا المستند على staging.

---

## 0) قبل البدء (Pre-flight)

- [ ] خذ نسخة احتياطية كاملة: `php artisan backup:run`
- [ ] انشر آخر كود: `git pull origin main` + `composer install --no-dev -o`
- [ ] **شغّل كل الترحيلات:** `php artisan migrate --force`
  - **متوقّع:** تكتمل كل migrations بلا خطأ. إن فشل أي migration، أوقف وأصلح أولاً.
- [ ] افحص السلامة قبل التفعيل: `php artisan data:integrity-check`
  - **متوقّع:** لا `branch_id_missing` ولا `branch_id_orphan`.
- [ ] تأكّد أن `queue:work` و`schedule:run` (cron) يعملان على staging.

---

## 1) الإعداد قبل قلب المفتاح (والمفتاح ما زال OFF)

> كل هذا يعمل و`BRANCHES_ENABLED=false` — البيانات تُختَم على الفرع الرئيسي وتبقى جاهزة.

- [ ] أنشئ فرعاً ثانياً من `/admin/branches` (مثال: كود `MAADI`, اسم "المعادي", عنوان, هاتف).
- [ ] من `/admin/branches` → "الأعضاء": أسند موظفاً/سكرتيراً وطبيباً للفرع الجديد.
  - أنشئ **أدمن اختبار** مُسنَد لفرع المعادي فقط (ليس super_admin).
- [ ] (اختياري) اضبط إعداداً خاصاً بالفرع: اسم العيادة/العنوان لفرع المعادي.
- [ ] أعد فحص السلامة: `php artisan data:integrity-check` → **نظيف**.

---

## 2) قلب المفتاح

- [ ] في `.env` (staging): `BRANCHES_ENABLED=true`
- [ ] `php artisan config:clear && php artisan optimize`
- [ ] (إن استخدمت OPcache) أعد ضبطه.

---

## 3) اختبارات العزل (الأهم)

### 3.1 عزل القوائم
- [ ] سجّل دخول بـ **أدمن المعادي** → افتح `/admin/bookings`, `/admin/invoices`, `/admin/visits`.
  - **متوقّع:** يرى بيانات فرع المعادي فقط (الحجوزات/الفواتير القديمة على الفرع الرئيسي لا تظهر).
- [ ] سجّل دخول بأدمن الفرع الرئيسي → يرى بيانات الفرع الرئيسي فقط.
- [ ] super_admin: مبدّل الفرع في الهيدر → اختر "كل الفروع" → يرى الجميع.

### 3.2 منع الوصول المتقاطع عبر الرابط (تم تأمينه برمجياً)
- [ ] كأدمن المعادي، خذ `id` فاتورة/حجز من الفرع الرئيسي وافتح `/admin/invoices/{id}` يدوياً.
  - **متوقّع:** صفحة **404** (لا تسريب). وبالعكس لأدمن الرئيسي مع بيانات المعادي.
- [ ] كأدمن المعادي افتح حجزاً يخصّ المعادي → **200** يعمل بشكل طبيعي.

### 3.3 المبدّل والصلاحيات
- [ ] أدمن مُسنَد لفرعين → المبدّل يُظهر الفرعين فقط؛ التبديل يغيّر البيانات المعروضة.
- [ ] أدمن غير super_admin لا يستطيع اختيار "كل الفروع" (يُرفض).
- [ ] الطبيب/السكرتير: المبدّل يظهر في الهيدر ويعمل (`/{panel}/switch-branch`).

---

## 4) الترقيم والإعدادات لكل فرع

- [ ] أنشئ حجزاً/فاتورة جديدة في **الفرع الرئيسي** → الرقم بالصيغة القديمة `BK-YYYYMM-####` / `INV-…`.
- [ ] أنشئ حجزاً/فاتورة جديدة في **المعادي** → الرقم يحمل كود الفرع `BK-MAADI-YYYYMM-####`.
  - **متوقّع:** لا تصادم، تسلسل مستقل لكل فرع.
- [ ] إن ضبطت إعداداً خاصاً بالفرع (اسم العيادة): تحقّق أن **فاتورة المعادي PDF** تطبع اسم/عنوان المعادي،
      وفاتورة الرئيسي تطبع الإعداد العام.

---

## 5) الحجز المواجِه للمريض + المواعيد

- [ ] من الموقع العام `/booking`: يظهر **مُنتقي الفرع** (لوجود فرعين). اختر المعادي.
  - **متوقّع:** المواعيد المتاحة تعكس جدول طبيب المعادي فقط؛ الحجز يُنسب للمعادي برقم مُرمَّز.
- [ ] من بوابة المريض `/{locale}/patient/bookings/create`: مُنتقي الفرع يظهر ويعمل بنفس المنطق.

---

## 6) التقارير

- [ ] كأدمن المعادي افتح `/admin/reports/financial` و`/admin/reports/revenue-analytics`.
  - **متوقّع:** أرقام فرع المعادي فقط (لا تسريب من الرئيسي).
- [ ] super_admin (كل الفروع) → التقارير تُجمّع كل الفروع.
- [ ] `/admin/reports/branch-comparison` → جدول مقارنة لكل فرع (حجوزات/زيارات/محصّل/متبقٍّ).

---

## 7) الأوامر المجدولة (cron) — يجب أن تعالج كل الفروع

- [ ] شغّل يدوياً:
  - `php artisan bookings:send-reminders`
  - `php artisan invoices:check-overdue`
  - `php artisan inventory:check-low-stock`
  - `php artisan satisfaction:send-surveys`
  - **متوقّع:** تعالج بيانات **كل الفروع** (ليس الفرع 1 فقط) — راجع المخرجات/السجل.
- [ ] `php artisan bookings:create-daily-visits` ثم تحقّق أن الزيارة الجديدة ورثت **فرع حجزها** (لا الفرع الافتراضي).

---

## 8) سلامة البيانات بعد التفعيل

- [ ] `php artisan data:integrity-check --alert`
  - **متوقّع:** لا `branch_id_missing` / `branch_id_orphan`.
- [ ] افحص `/admin/diagnostics` و`GET /health` → سليم.

---

## 9) الرجوع السريع (Rollback)

إن ظهر أي خلل:
- [ ] `BRANCHES_ENABLED=false` في `.env` → `php artisan config:clear && php artisan optimize`.
  - **النتيجة:** يعود النظام لسلوك العيادة الواحدة فوراً (الـ global scope يصبح no-op).
  - البيانات تبقى سليمة (كل صف يحمل `branch_id` صحيحاً)؛ لا فقدان.

---

## 10) معايير القبول للإنتاج (Go / No-Go)

اعتبرها جاهزة للإنتاج فقط إذا:
- ✅ بنود §3 (العزل + منع الوصول المتقاطع) نجحت كلها.
- ✅ §4 الترقيم لكل فرع بلا تصادم.
- ✅ §5 الحجز المواجِه يحترم الفرع المختار.
- ✅ §6 التقارير لا تُسرّب.
- ✅ §7 الـ cron عالج كل الفروع.
- ✅ §8 فحص السلامة نظيف.

عند الإنتاج: كرّر §0–§2 (نسخة احتياطية → migrate → flip) في نافذة صيانة، ثم §8 سريعاً.
