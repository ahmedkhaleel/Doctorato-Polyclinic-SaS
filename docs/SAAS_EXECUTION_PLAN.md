**Date:** 2026-06-10
**القرار المعماري المعتمد:** كود واحد مشترك + subdomain وقاعدة بيانات
مستقلة لكل عيادة (Database-per-Tenant عبر `stancl/tenancy`) + إدارة

**مرجع التحليل والمفاضلة:** `docs/SAAS_TRANSFORMATION_PLAN.md`

## الصورة النهائية المستهدفة

```
                    doctorato.net (تسويقي + تسجيل)
                    my.doctorato.net (لوحة المنصة — أنت فقط)
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
     clinic-a.doctorato  clinic-b.doctorato  clinic-c...
              │               │               │
   ┌──────────┴───────────────┴───────────────┴──────────┐
   │   تطبيق Laravel واحد على VPS (يديره Forge)           │
   │                                                      │
   │   MySQL: doctorato_central  ← العيادات/الباقات/الاشتراكات
   │          tenant_clinic_a    ← مخطط العيادة الكامل (325 جدول)
   │          tenant_clinic_b
   │          tenant_...
   │   Redis: كاش + جلسات + كيو (مفصولة ببادئة لكل عيادة)  │
   └──────────────────────────────────────────────────────┘

  اشتراك جديد → صف tenant → قاعدة تُنشأ → migrate تلقائي →
  أدمن أولي → رسالة ترحيب — كل ذلك آلياً بدون تدخل يدوي.
```

**مبدأ التنفيذ:** نفس منهجية مراحل CRM — مرحلة ← اختبارات ← معاينة ←
نشر ← ثم المرحلة التالية. لا ننتقل لمرحلة قبل اكتمال سابقتها بمعاييرها.

# المرحلة S0 — تجهيز البنية التحتية (Forge + VPS)

> **الهدف:** سيرفر إنتاجي جاهز ونظيف قبل لمس أي كود.
> **المدة التقديرية:** يوم إلى يومان.
> **المطلوب منك (المالك) — لا يمكنني عملها نيابة عنك:**
> 1. حساب [Hetzner](https://hetzner.com) وشراء **CX32** (4 vCPU / 8GB /
>    Ubuntu 24.04) — اختر موقع Falkenstein أو Nuremberg.
> 2. حساب [Laravel Forge](https://forge.laravel.com) — خطة Hobby تكفي
>    (12$/شهر).
> 3. وصول لإدارة DNS للدومين doctorato.net.

## S0.1 ربط السيرفر بـ Forge
- في Forge: Create Server → Hetzner (بمفتاح API) أو Custom VPS.
- النوع: **App Server** (يثبّت: Nginx, PHP 8.3, MySQL 8, Redis,
  Supervisor, Node 22, Composer, UFW, Fail2ban تلقائياً).
- تفعيل أقساط OPcache الافتراضية (مشكلة cPanel القديمة تنتهي هنا —
  Forge يعمل reload لـ FPM مع كل deploy).

## S0.2 DNS والشهادات
- سجلات DNS:
  - `A  @              → IP السيرفر`
  - `A  *.doctorato.net → IP السيرفر`  ← **wildcard هو مفتاح الـ subdomains**
  - `A  my             → IP السيرفر`
- في Forge: موقع جديد `doctorato.net` مع **aliases** للـ wildcard،
  ثم SSL → Let's Encrypt → أدخل `doctorato.net, *.doctorato.net`
  (يتطلب DNS challenge — Forge يدعمه مع مزودي DNS الشائعين، وإلا
  Cloudflare DNS مجاناً هو الأسهل).

## S0.3 الأمان والأساسيات
- SSH بمفتاح فقط (Forge يفرضه افتراضياً) + 2FA على حسابي Forge وHetzner.
- MySQL على localhost فقط (الافتراضي).
- إنشاء قاعدة `doctorato_central` ومستخدم خاص بها.
- **مستخدم MySQL للتطبيق يحتاج صلاحية `CREATE`** (لأن tenancy ينشئ
  قاعدة لكل عيادة) — ننشئ مستخدم `doctorato_app` بصلاحيات على
  `tenant_%.*` و `doctorato_central.*` فقط.

## S0.4 النسخ الاحتياطي والمراقبة
- Hetzner Backups (20% من سعر السيرفر) — snapshot يومي للسيرفر كاملاً.
- حساب Backblaze B2 (سننفذ ربط spatie/backup به في S1).
- UptimeRobot (مجاني): مراقبة `https://doctorato.net/health`.

## ✅ معايير اكتمال S0
- [ ] فتح `https://anything.doctorato.net` يصل للسيرفر بشهادة صحيحة.
- [ ] `php -v` = 8.3، `redis-cli ping` = PONG، `node -v` = 22.
- [ ] Deploy تجريبي لمستودع فارغ ينجح من Forge.

# المرحلة S1 — أساس الـ Tenancy في الكود (الأكبر والأهم)

> **الهدف:** النظام الحالي يعمل بنمط قاعدة-لكل-عيادة دون كسر أي ميزة.
> **المدة التقديرية:** 2–3 أسابيع عمل منظم.
> **الفرع:** `feature/tenancy-foundation` — لن يُدمج إلا باكتمال
> الاختبارات كاملة.

## S1.1 تثبيت وتهيئة stancl/tenancy v3
- `composer require stancl/tenancy`.
- نموذج `Tenant` (في القاعدة المركزية) ببيانات العيادة + `Domain`.
- التعريف بالـ subdomain: `clinic-a.doctorato.net` → tenant `clinic-a`.
- **Bootstrappers** المفعّلة:
  - `DatabaseTenancyBootstrapper` — توصيل قاعدة العيادة تلقائياً.
  - `CacheTenancyBootstrapper` — بادئة كاش لكل عيادة (Redis).
  - `FilesystemTenancyBootstrapper` — عزل `storage/` لكل عيادة
    (**حاسم للـ PHI**: ملفات الأشعة/الصور تصبح
    `storage/tenant-{id}/...` — يتكامل مع S1 الموجود: التقديم المصادق
    عبر private disk يعمل كما هو).
  - `QueueTenancyBootstrapper` — كل Job يحمل سياق عيادته (نفس درس
    `BranchContext` في الكرون حرفياً).

## S1.2 فصل الميجريشن: مركزي vs عيادة
- نقل **كل** الـ 325 ميجريشن الحالية إلى `database/migrations/tenant/`.
- `database/migrations/` المركزي يبدأ نظيفاً بـ: tenants, domains,
  plans, subscriptions, platform_invoices, instance_health.
- أوامر التشغيل الجديدة في كل deploy:
  `php artisan migrate --force` (مركزي) ثم
  `php artisan tenants:migrate` (كل قواعد العيادات).
- عيادة جديدة → `tenants:migrate` عليها تلقائياً عند الإنشاء (event
  `TenantCreated` → pipeline: إنشاء القاعدة → migrate → seed أساسي →
  أدمن أولي).

## S1.3 فصل الراوتات
- `routes/tenant.php`: **كل** راوتات النظام الحالية (web, patient,
  admin, doctor, secretary, webmaster) — تعمل فقط تحت subdomain عيادة.
- `routes/web.php` المركزي: الموقع التسويقي + التسجيل + `/health`
  المركزي + لوحة المنصة (`my.`).
- حارس: middleware يمنع فتح راوتات العيادات على الدومين المركزي
  والعكس (اختبارات تغطيه).

## S1.4 النقاط الحساسة في هذا الريبو تحديداً (من معرفتي بالكود)
| النقطة | المعالجة |
|---|---|
| `Setting` (مفاتيح Agora/Paymob/الإعدادات) | تعيش في قاعدة كل عيادة — تعمل **كما هي** بلا تعديل، وكل عيادة بمفاتيح دفعها الخاصة |
| `ModuleManager` | per-tenant بطبيعته الآن — يصبح ذراع تنفيذ الباقات |
| الكرون (`console.php` — 15+ أمراً مجدولاً) | تتحول إلى `tenants:run` أو حلقة على العيادات النشطة فقط؛ نفس نمط ALL-BRANCHES الموثق في CLAUDE.md |
| `public/build` داخل الريبو | **يُحذف من الريبو** بعد الانتقال — Forge يبني `npm run build` في كل deploy (يُحدَّث CLAUDE.md وCI) |
| الكيو | Redis + Horizon، وكل Job ملوّن بعيادته تلقائياً عبر Bootstrapper |
| `/health` | يبقى لكل عيادة (uptime لكل عميل) + `health` مركزي مجمّع |
| Multi-branch | لا تعارض — الفروع داخل قاعدة كل عيادة، والـ kill-switch لكل عيادة |
| الاختبارات (310 ملفاً) | تُهيأ `TestCase` لإنشاء tenant تجريبي — **معيار النجاح: الـ 1681 اختباراً خضراء تحت tenancy** |

## S1.5 اختبارات المرحلة (جديدة)
- إنشاء tenant ينشئ قاعدة + يشغّل الميجريشن + seed.
- عزل تام: بيانات عيادة A لا تظهر إطلاقاً في B (اختبار صريح
  cross-tenant على المرضى والحجوزات والإعدادات).
- الكاش والجلسات معزولة (مفاتيح ببادئة مختلفة).
- Job في كيو عيادة A ينفَّذ على قاعدة A حتى لو dispatch من سياق آخر.
- راوت عيادة على الدومين المركزي → 404، والعكس.

- [ ] كامل الـ test suite الحالي أخضر تحت tenancy.

      كاملة في كلتيهما دون تداخل.
- [ ] deploy واحد من Forge يحدّث الاثنتين معاً (migrate مركزي + tenants).

# المرحلة S2 — لوحة المنصة (الحساب فوق السوبر أدمن)

> **الهدف:** لوحة `my.doctorato.net` تدير كل شيء: عيادات، باقات،
> اشتراكات، تنصيب آلي.
> **المدة:** أسبوع–أسبوعان.

## S2.1 الهوية والصلاحية
- حارس مصادقة منفصل `platform` (جدول `platform_users` مركزي) —
  **معزول تماماً** عن مستخدمي العيادات؛ 2FA إلزامي (TOTP).
- لا أي صلاحية للوحة المنصة على بيانات المرضى — تشاهد أرقاماً مجمعة فقط.

## S2.2 الشاشات (Inertia — نفس معايير تصميم الكوكبيت المعتمدة)
1. **Dashboard:** عدد العيادات النشطة/المتأخرة/الموقوفة، MRR، انتهاءات
   قادمة، آخر heartbeat لكل عيادة.
2. **العيادات:** قائمة + إنشاء (اسم، slug للـ subdomain، بيانات تواصل،
   باقة) → زر **Provision** ينفّذ السلسلة: قاعدة → migrate → seed →
   أدمن أولي → بريد/واتساب ترحيبي ببيانات الدخول.
3. **الباقات:** CRUD — الوحدات (checkboxes للـ 8 وحدات) + الحدود
   (أطباء/مستخدمين/فروع/تخزين/ميزانية AI) + السعر شهري/سنوي.
4. **الاشتراكات:** لكل عيادة — بدء/انتهاء/تجديد/إيقاف/مهلة، وسجل تدقيق
   لكل تغيير.
5. **عيادة (Show):** استهلاكها مقابل حدودها، نسختها، صحتها، أزرار:
   تجديد، ترقية باقة، إيقاف مؤقت، Login-as-admin (بسجل تدقيق وإذن صريح).

## S2.3 صلاحيات المنصة على ModuleManager
- عند حفظ الباقة/الاشتراك → مزامنة فورية: داخل سياق العيادة
  `ModuleManager::enable/disable` حسب باقة العيادة (نفس الدوال
  المختبرة).

# المرحلة S3 — فرض الاشتراك والحدود (Enforcement)

> **الهدف:** انتهاء الاشتراك والحدود تُفرض تلقائياً وبأدب — دون حذف
> بيانات أبداً.
> **المدة:** أسبوع.

## S3.1 حالات الاشتراك ودورة حياته
```
trial (14ي) → active → [قبل 14ي + 3ي: تذكير] → انتهاء →
grace (7ي، بانر أصفر) → readonly (قراءة + تصدير فقط + شاشة تجديد)
                       → تجديد في أي لحظة يعيد active فوراً
```
- **قاعدة ثابتة: لا حذف بيانات مرضى أبداً** — readonly للأبد حتى
  التجديد أو طلب تصدير نهائي.

## S3.2 التنفيذ
- Middleware `subscription.state` على كل راوتات العيادة: يقرأ حالة
  اشتراك العيادة من القاعدة المركزية (**مع كاش 10 دقائق** — لا استعلام
  مركزي في كل طلب).
- `readonly`: يسمح GET + تصدير التقارير، يمنع POST/PUT/DELETE
  (باستثناء مسار التجديد)، بانر دائم.
- `PlanEnforcer::can('doctors'|'users'|'branches')` عند نقاط الإنشاء —
  نفس نمط `AiGate::authorize` المختبر؛ تجاوز الحد = رسالة ترقية أنيقة
  وليس خطأ خام.
- ميزانية AI لكل عيادة: ربط `ai_monthly_budget_usd` الموجود بحد الباقة.
- شاشة "اشتراكي" في أدمن كل عيادة: الباقة، الاستهلاك مقابل الحدود،
  الانتهاء، وزر طلب تجديد/ترقية.

## ✅ معايير اكتمال S3
- [ ] اختبارات: active يمر، grace يمر مع بانر، readonly يمنع الكتابة
      ويسمح القراءة والتصدير، التجديد يرفع الحظر فوراً.
- [ ] اختبار حدود: الطبيب رقم N+1 يُمنع برسالة ترقية.
- [ ] معاينة متصفح لكل الحالات الثلاث.

# المرحلة S5 — تهجير العيادات الحالية من cPanel

> **الهدف:** نقل عيادة doctorato.net الحالية (وأي نسخ أخرى) إلى المنصة
> دون فقد دقيقة عمل.
> **المدة:** يوم لكل عيادة (معظمه انتظار DNS).

## خطوات لكل عيادة (Runbook)
1. إنشاء tenant فارغ لها في المنصة (دون provision قاعدة).
2. تجميد الكتابة على القديم ليلاً (وضع صيانة) + `mysqldump`.
3. استيراد الـ dump إلى `tenant_clinicX` — **المخطط واحد، لا تحويل
   بيانات** (نفس الكود!) ثم `tenants:migrate --tenants=clinicX`
   لأي ميجريشن أحدث.
4. نسخ `storage/` إلى مسار الـ tenant.
5. تبديل DNS للدومين/الـ subdomain نحو السيرفر الجديد (TTL منخفض
   مسبقاً)، والقديم يحوّل redirect.
6. فحص قبول: دخول، حجز، فاتورة، عرض ملف PHI، إشعار واتساب.
7. **خطة التراجع:** القديم يبقى مجمداً أسبوعاً — أي مشكلة = إعادة DNS
   فوراً (لا حذف قبل أسبوعين).

## ✅ معايير اكتمال S5
- [ ] العيادة الحالية تعمل من المنصة بكل ميزاتها وبياناتها.
- [ ] حساب cPanel القديم بلا حركة لمدة أسبوعين ثم يُلغى.
