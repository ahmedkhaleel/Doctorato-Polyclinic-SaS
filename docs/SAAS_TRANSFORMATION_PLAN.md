# تحويل Doctorato إلى منصة SaaS — الخطة المعمارية الكاملة

**Status:** Proposed — بانتظار اعتماد المالك
**Date:** 2026-06-10
**Deciders:** مالك المنصة (Platform Owner)

> الهدف: بدلاً من نسخ الكود لكل عيادة بلا تحكم ولا تاريخ انتهاء، نبني طبقة
> "منصة" فوق النظام الحالي: حساب أعلى من السوبر أدمن يتحكم في كل عيادة —
> الباقة، الوحدات المفعّلة، الحدود، مدة الاشتراك، الإيقاف والتجديد — من
> لوحة واحدة.

---

## 1. خريطة النظام الحالي (Current-State Map)

حجم النظام (مقاس فعلياً من الكود):

| المكوّن | العدد |
|---|---|
| Models | 195 |
| Migrations | 325 |
| Controllers | 300 |
| صفحات Vue (Inertia) | 545 |
| ملفات اختبار | 310 |
| اللوحات (Panels) | 6: Frontend, Patient, Doctor, Secretary, Admin, Webmaster |

**أصول معمارية موجودة بالفعل تخدم التحول إلى SaaS** (هذه نقطة قوتك الكبرى):

1. **`ModuleManager`** — تفعيل/تعطيل 8 وحدات طبية لكل تنصيبة
   (derma, dental, pediatric, obgyn, psychiatry, neurology, physiotherapy,
   telemedicine). هذا هو بالضبط مفهوم "الباقة تحدد الخدمات" — جاهز ولا
   يحتاج إعادة بناء، يحتاج فقط من يأمره من الأعلى (الرخصة).
2. **`Setting`** — جدول key/value لكل شيء قابل للضبط، مع تشفير للمفاتيح
   الحساسة، ودعم Override لكل فرع. نفس النمط يصلح لتخزين الرخصة.
3. **Multi-Branch بمفتاح إيقاف** (`BRANCHES_ENABLED`) — أثبتنا أن الكود
   يقبل التوسيم والعزل (`BelongsToBranch`) بدون كسر أي شيء. نفس الفلسفة
   تنطبق على أي توسيع مستقبلي.
4. **`AiGate` + `AiCostMeter`** — نموذج جاهز لـ"ميزانية شهرية + حدود
   استخدام + كسر الدائرة عند التجاوز". سننسخ نفس النمط لحدود الباقات.
5. **بوابات دفع جاهزة** (Paymob + Stripe) — ستُعاد تسميتها في طبقة
   المنصة لتحصيل الاشتراكات نفسها.
6. **نمط النشر الحالي**: git push → cPanel deploy، و`public/build`
   داخل الريبو لأن الاستضافة المشتركة بلا npm.

**المشكلة الحالية بدقة:**
- عيادة جديدة = نسخة كاملة من الكود + قاعدة بيانات مستقلة.
- لا يوجد تاريخ انتهاء: العميل يدفع مرة ويستخدم للأبد.
- لا تحكم مركزي: تغيير باقة عميل = دخول يدوي على تنصيبته.
- لا يوجد "حساب فوق السوبر أدمن": السوبر أدمن في كل تنصيبة هو أعلى سلطة.

## 2. الخيارات المعمارية الثلاثة (Options Considered)

### الخيار A — "أسطول منصّبات مُدارة" (Managed Instances + Control Plane)

كل عيادة تبقى **تنصيبة مستقلة بقاعدة بياناتها** (كما تفعل الآن)، لكن نبني
**لوحة منصة مركزية** (تطبيق Laravel صغير منفصل على نطاق مثل
`my.doctorato.net`) هي "الحساب فوق السوبر أدمن":

- تُصدر **رخصة موقّعة رقمياً** لكل عيادة: الباقة + الوحدات + الحدود +
  تاريخ الانتهاء.
- كل تنصيبة تتحقق من الرخصة محلياً (بدون إنترنت) وتتصل بالمنصة مرة
  يومياً (heartbeat) لتجديد الرخصة وإرسال إحصاءات غير طبية.
- انتهى الاشتراك؟ التنصيبة تدخل وضع القراءة فقط + شاشة تجديد، تلقائياً.

| البُعد | التقييم |
|---|---|
| التعقيد | **منخفض** — لا تغيير في بنية النظام إطلاقاً |
| التكلفة | منخفضة (تستمر على cPanel الحالي) |
| عزل بيانات المرضى (PHI) | **ممتاز** — كل عيادة قاعدة مستقلة بالكامل |
| سرعة الوصول للسوق | **أسابيع** وليس شهوراً |
| عبء التشغيل | متوسط — تحديث الكود يتم لكل تنصيبة (git pull لكل واحدة، قابل للأتمتة) |

**Pros:** أسرع حل، صفر مخاطرة على الكود الحالي، عزل طبي مثالي، يعمل على
استضافتك الحالية، يحل مشكلتك العاجلة (الانتهاء + التحكم) فوراً.
**Cons:** التحديثات تتكرر لكل عميل (تُحَل بسكربت نشر جماعي)، لا توجد
لوحة بيانات موحّدة فورية (تُحَل بالـ heartbeat).

### الخيار B — قاعدة بيانات لكل عميل في تنصيبة واحدة (Database-per-Tenant)

كود واحد منشور مرة واحدة على **VPS**، وكل عيادة لها **subdomain**
(`clinic1.doctorato.net`) و**قاعدة بيانات خاصة**، عبر حزمة ناضجة مثل
`stancl/tenancy`:

- قاعدة مركزية: tenants, domains, plans, subscriptions.
- عند كل طلب: تحديد العيادة من النطاق → توصيل قاعدة بياناتها تلقائياً.
- تحديث واحد يصل للجميع فوراً؛ لوحة المنصة مدمجة طبيعياً.

| البُعد | التقييم |
|---|---|
| التعقيد | متوسط — bootstrapping للتينانسي + جعل الكيو والتخزين tenant-aware |
| التكلفة | VPS (يبدأ ~10-20$/شهر) بدل/بجانب cPanel |
| عزل PHI | **ممتاز** — قاعدة لكل عيادة |
| سرعة الوصول | 2-3 أشهر عمل منظم |
| عبء التشغيل | **الأدنى على المدى الطويل** — نشر واحد للجميع |

**Pros:** هذا هو شكل الـ SaaS الحقيقي طويل الأمد؛ onboarding عيادة
جديدة = صف في جدول + زر؛ نسخ احتياطي لكل عيادة على حدة.
**Cons:** يتطلب مغادرة الاستضافة المشتركة؛ `migrate` يعمل لكل قاعدة؛
يلزم اختبار شامل لمسارات الملفات والكيو والكرون لتصبح tenant-aware.

### الخيار C — قاعدة واحدة بعمود tenant_id (Pooled / Shared Database)

مثل نمط الفروع لكن على مستوى العيادات: عمود `tenant_id` في كل الجداول.

| البُعد | التقييم |
|---|---|
| التعقيد | **مرتفع جداً** — توسيم ~325 جدولاً ومراجعة كل استعلام |
| التكلفة | الأدنى بنية تحتية |
| عزل PHI | **الأضعف** — نطاق واحد منسي = تسريب بيانات مرضى بين عيادات |
| سرعة الوصول | أشهر طويلة + مخاطرة عالية |

**مرفوض لنظام طبي.** خطأ واحد في scope = كارثة خصوصية. النسخ الاحتياطي
والاستعادة لعيادة واحدة شبه مستحيل عملياً.

## 3. القرار الموصى به (Decision)

> **استراتيجية مرحلية: A الآن ← B لاحقاً. C مرفوض نهائياً.**

- **المرحلة 0 (فوراً):** ابنِ طبقة الرخص والتحكم (الخيار A). تحل مشكلتك
  العاجلة — التحكم والانتهاء — خلال أسابيع وبدون لمس بنية النظام،
  وتبدأ تحصيل اشتراكات حقيقية.
- **لاحقاً عند 10+ عيادات:** انقل العملاء الجدد إلى الخيار B على VPS.
  كل ما بنيته في المرحلة 0 (الباقات، الرخص، لوحة المنصة) يُعاد استخدامه
  كما هو — فقط طريقة "تشغيل" العيادة تتغير.

السبب: أنت مطوّر منفرد، السوق ينتظر، والنظام الحالي ناضج ومُختبر
(1681 اختباراً). أقصر طريق للإيراد هو طبقة تحكم فوق ما يعمل اليوم،
وليس إعادة هندسة.

### 4.3 الرخصة الموقّعة (License Token) — قلب الحل

- **الصيغة:** JWT موقّع بمفتاح **Ed25519 خاص** يعيش فقط على سيرفر
  المنصة. المفتاح **العام** يوضع داخل كود العيادة (لا سرّ فيه).
- **المحتوى (Claims):**

```json
{
  "tenant": "clinic-alfa",
  "plan": "pro",
  "modules": ["derma", "dental", "telemedicine"],
  "limits": { "doctors": 5, "branches": 1, "users": 10,
              "storage_gb": 5, "ai_monthly_usd": 10 },
  "issued_at": "2026-06-10T00:00:00Z",
  "expires_at": "2026-07-10T00:00:00Z",
  "grace_days": 7
}
```

- **لماذا التوقيع الرقمي؟** التنصيبة تتحقق من الرخصة **محلياً وبدون
  إنترنت** (مهم لعيادات اتصالها ضعيف)، ولا يمكن للعميل تزوير رخصة أو
  تمديدها لأن التوقيع يكسر. حتى لو فتح قاعدة البيانات وعدّل التاريخ —
  التوقيع لن يطابق.
- **التجديد:** التنصيبة تطلب رخصة محدثة في الـ heartbeat اليومي. أنت
  تجدد الاشتراك في لوحة المنصة → الرخصة الجديدة تصل تلقائياً خلال
  24 ساعة كحد أقصى (أو فوراً بزر "Sync الآن" عند العميل).

### 4.4 جانب العيادة (تعديلات هذا الريبو — صغيرة ومحصورة)

1. **`app/Services/Platform/LicenseService.php`**
   - يقرأ التوكن من `Setting('platform_license')`.
   - `verify()`: توقيع + انتهاء (مع المهلة grace) — أوفلاين بالكامل.
   - `state()`: `active | grace | expired | unlicensed`.
   - نتيجة التحقق تُكاش 10 دقائق (لا تكلفة على كل طلب).

2. **`app/Http/Middleware/EnforceLicense.php`** — على لوحات
   admin/doctor/secretary/patient:
   - `active`: مرور طبيعي.
   - `grace`: مرور + بانر أصفر "اشتراكك انتهى، لديك X أيام".
   - `expired`: **وضع القراءة فقط** — يسمح بعرض البيانات وتصدير
     التقارير، يمنع الإنشاء/التعديل، ويحوّل لصفحة تجديد.
     **لا حذف بيانات أبداً** (التزام أخلاقي وقانوني — بيانات مرضى).

3. **`app/Services/Platform/PlanEnforcer.php`**
   - عند كل مزامنة رخصة: الوحدات خارج الباقة → `ModuleManager::disable`
     (نفس الآلية المختبرة الموجودة، لا UI جديد).
   - الحدود تُفرض عند نقاط الإنشاء فقط (إنشاء طبيب جديد/مستخدم/فرع):
     `PlanEnforcer::can('doctors')` — نفس نمط `AiGate::authorize` حرفياً.

4. **`platform:heartbeat`** (أمر كرون يومي موجود في `console.php`):
   - يرسل: نسخة التطبيق، أعداد فقط (أطباء/مستخدمين/مرضى)، ملخص `/health`.
   - يستقبل: رخصة محدثة إن وُجدت.
   - فشل الاتصال لا يوقف شيئاً — الرخصة المحلية هي الحكم حتى انتهائها.

5. **شاشة "الاشتراك"** في إعدادات الأدمن: الباقة الحالية، الوحدات،
   الاستهلاك مقابل الحدود، تاريخ الانتهاء، زر Sync، وتعليمات التجديد.

> **مبدأ حاسم:** حساب المنصة لا يدخل بيانات المرضى إطلاقاً. الـ heartbeat
> أرقام مجمّعة فقط. عزل الـ PHI الكامل هو ميزة تسويقية لك أمام العيادات.

### 4.5 الباقات المقترحة (قابلة للتعديل من لوحة المنصة)

| | Basic | Pro | Enterprise |
|---|---|---|---|
| الوحدات الطبية | 2 من اختياره | الكل | الكل |
| التطبيب عن بعد | — | ✓ | ✓ |
| الأطباء | 3 | 10 | بلا حد |
| الفروع | 1 | 1 | متعدد (`BRANCHES_ENABLED`) |
| الذكاء الاصطناعي | — | ميزانية 10$/شهر | ميزانية مخصصة |
| المستخدمون (طاقم) | 5 | 15 | بلا حد |

لاحظ: كل صف في هذا الجدول يقابله شيء **موجود فعلاً** في الكود
(ModuleManager / BRANCHES_ENABLED / ai_monthly_budget_usd) — الباقة
مجرد "ريموت كنترول" لما هو مبني.

### 4.6 أتمتة تنصيب عيادة جديدة (Onboarding Script)

سكربت `provision-clinic.sh` على السيرفر:
1. ينسخ الريبو إلى مجلد/دومين العميل (`clinicX.doctorato.net`).
2. ينشئ قاعدة بيانات + مستخدم + `.env`.
3. `migrate --force` + Seeders الأساسية (بدون Demo).
4. يسجّل العيادة في لوحة المنصة (API) → يستلم الرخصة → يحقنها.
5. ينشئ حساب admin أولي ويرسل بيانات الدخول.

النتيجة: عيادة جديدة في **دقائق** بدلاً من نسخ يدوي، ومربوطة بالمنصة
منذ اللحظة الأولى. وسكربت `update-fleet.sh` يعمل `git pull + migrate`
لكل التنصيبات بالتتابع (التحديث الجماعي).

## 5. المرحلة 1: التحصيل والفوترة (بعد تشغيل المرحلة 0)

- اشتراكات Paymob المتكررة (السوق المصري) + تحويل بنكي بتفعيل يدوي

- تذكير تجديد تلقائي: 14 يوماً و3 أيام قبل الانتهاء (واتساب/بريد —
  نفس قنوات الـ hub الموجودة لديك خبرة بها).

## 6. المرحلة 2: الانتقال إلى Database-per-Tenant (عند النمو)

عندما يصبح عدد العيادات مرهقاً للتحديث الجماعي (~10+):

1. VPS (مثل Hetzner/DigitalOcean) + Laravel Forge أو Ploi للإدارة.
2. حزمة `stancl/tenancy`: قاعدة مركزية (هي نفسها قاعدة لوحة المنصة) +
   قاعدة لكل عيادة + subdomain routing.
3. جعل التخزين tenant-aware (`storage/tenant-{id}/`) والكيو يحمل سياق
   العيادة — نفس ما فعلناه مع `BranchContext` في الكرون حرفياً.
4. العملاء الجدد يُنصّبون على المنصة الجديدة؛ القدامى يُهاجرون عيادة
   عيادة (استيراد قاعدة بياناتهم كما هي — لا تحويل بيانات لأن المخطط
   واحد).
5. لوحة المنصة لا تتغير — فقط يضاف لها زر "إنشاء tenant" بدل سكربت
   التنصيب.

## 7. الأمان والخصوصية (Security Posture)

- **عزل PHI:** قاعدة مستقلة لكل عيادة في كل المراحل (A وB كلاهما).
- **الرخص:** Ed25519، المفتاح الخاص لا يغادر سيرفر المنصة، دوران مفاتيح
  سنوي مدعوم (kid في رأس التوكن).
- **الـ heartbeat:** HTTPS + توقيع HMAC بسر لكل عيادة، أرقام مجمعة فقط.
- **انتهاء الاشتراك ≠ حذف بيانات:** وضع قراءة فقط + تصدير متاح دائماً.
  (يحمي سمعتك ويتوافق مع أخلاقيات البيانات الطبية).
- **لوحة المنصة:** 2FA إلزامي لحساب المالك، سجل تدقيق لكل إصدار/سحب رخصة.

## 8. ما الذي سنعيد النظر فيه مع النمو (Revisit Triggers)

| المؤشر | القرار المُعاد فتحه |
|---|---|
| 10+ عيادات نشطة | بدء المرحلة 2 (tenancy على VPS) |
| طلب عيادات لتقارير عبر-الفروع سحابية | Data warehouse مجمّع (بموافقة وإخفاء هوية) |
| فريق دعم > شخص واحد | أدوار داخل لوحة المنصة (owner/support/billing) |
| عملاء خارج مصر/السعودية | Stripe Billing + ضرائب لكل دولة |
